## 1. Security — confirmed gaps, direct from the code

| # | Finding | Severity | Evidence |
|---|---|---|---|
| 1 | **No rate limiting anywhere** — signup, login, message-send, review-submit are all unthrottled at the app layer. | High | No `middleware.ts`, no rate-limit library in `package.json`, confirmed by grep. Supabase Auth has its own internal throttling on `/signup`/`/token`, but our own routes (`/api/reviews`, `/api/connect/[id]`, `/api/conversations/[id]/messages`) have none. |
| 2 | **No security headers configured** — no CSP, no `X-Frame-Options`, no `Referrer-Policy`. | Medium | No `next.config.js` exists at all in this repo. Vercel adds some defaults (HSTS) but nothing app-specific. |
| 3 | **No server-side password strength requirement** — only a client-side `minLength={6}` on the login form; the signup API route itself performs no length/strength check, relying entirely on whatever Supabase Auth's own default is. | Medium | `grep` for `minLength`/`password.length` found exactly one client-side check. |
| 4 | **`/api/search` has no pagination** — returns every matching row, unbounded. | Medium (perf, not exploit) | No `limit`/`offset` anywhere in `app/api/search/route.ts` or `app/search/page.tsx`. At 40 teachers this is invisible; it won't stay that way. |
| 5 | **No report/block mechanism in messaging.** | High (trust & safety) | `grep -rn "report\|block"` across the messaging UI/API returns nothing. Real strangers can now message each other with zero recourse beyond emailing the site owner. |
| 6 | **No off-platform-contact-leakage detection in messages** — a message body can contain a phone number or external contact info with no flag, unlike the profanity filter which does scan content. | Low-medium | `lib/profanity.ts` exists and is wired in; nothing equivalent exists for phone/email-in-message-body detection. |
| 7 | Already documented, still true: no email verification enforcement gap, no CSRF token scheme, `GOTRUE_MAILER_AUTOCONFIRM` concern — see `docs/05-architecture-review.md` §A.1, unchanged. | — | Carried over, not re-verified line-by-line this pass. |

**What's already solid** (confirmed, not assumed): RLS enabled and participant-scoped on every new table added this session (`conversation`, `message`), narrow `SECURITY DEFINER` functions used consistently instead of broad table grants for anything sensitive (`reveal_teacher_contact`, `admin_add_teacher`, `get_conversation_partner_email`, `mark_conversation_read`), profanity filtering on both reviews and messages, admin actions audit-logged (`admin_audit_log`), session cookies are `httpOnly`+`secure`(prod)+`sameSite=lax`, and the three real production bugs found this session (localhost email links, insecure-redirect warning, Brevo IP block) are all fixed and verified live.

## 2. Feature gaps vs. real competitors (sourced research, not generic "best practice")

A dedicated research pass looked at Preply, Superprof, Urban Company, Practo, Sulekha, and UrbanPro — not to find one company TeacherCircle should copy wholesale (none of them run the same "free listing + first-message-then-reveal" model TeacherCircle does), but to pull out the specific, evidenced mechanisms worth adapting:

1. **Verification tiers vary hugely, and the badge should say which tier you're at.** Preply does government-ID + credential upload (blue check) but explicitly *no* criminal background check. Urban Company does third-party background checks (via AuthBridge) plus an ongoing minimum-rating bar to stay listed. Practo cross-checks a real registry number (state medical council / NMC) against an external authority — the strongest, most objectively-checkable model of the five, and the most transferable to teachers if a public teaching-credential registry exists in the markets TeacherCircle serves. TeacherCircle currently has **zero** verification of any kind on a teacher profile beyond "an email address exists." A `photo_url` column has existed on `teacher_profile` since the original schema and has never been wired to anything.
2. **Reviews should be gated to a real, verifiable interaction, or they're easy to game.** Preply only allows a review from a student who *paid* for a lesson with that specific tutor. TeacherCircle already does the closest available equivalent — a review requires a prior `contact_request` — which is good and already matches this principle; worth keeping and not weakening.
3. **Response-time and completed-interaction signals are cheap, high-trust additions.** Preply surfaces "replies within 24h"; Urban Company enforces a minimum customer rating to stay listed. TeacherCircle already has the raw data to compute "responds within X hours" (message timestamps) and could surface it on a teacher card with no new schema.
4. **A visible in-app report + block mechanism is the baseline, not a nice-to-have**, once strangers can message each other — confirmed as standard across the general marketplace trust-and-safety literature (not company-specific, but consistently cited). This is genuinely missing today (see Security finding #5 above) and is the single highest-priority gap this review found.
5. **Explicit gap in the research itself, disclosed rather than papered over**: no 2026 source was found that specifically standardizes age-verification or parental-consent flows for a *tutoring* platform (as opposed to general social platforms). Since TeacherCircle's messaging can put a parent/guardian on one side and an adult tutor on the other, this is a genuine open question worth raising with a lawyer, not something any competitor's practice already answers — flagging it rather than guessing at a "standard" that doesn't demonstrably exist.
6. **SEO is completely unbuilt** and is realistically TeacherCircle's main growth channel as a free directory (no commission funding paid acquisition). No per-teacher `<meta>` tags, no `sitemap.xml`, no `robots.txt`, no structured data. This was flagged as a suggestion before messaging shipped and remains untouched.

## 3. UX / "looks and feels" — carried forward, not yet re-prioritized

From the earlier suggestions list, still outstanding: dark mode (system-preference-aware), loading skeletons instead of blank states, saved/favorite teachers, richer search filters (price range, minimum rating, online-vs-in-person). Nothing new added here this pass — the security and trust-and-safety findings above are more urgent than visual polish at this point given real strangers can now message each other with no report/block path.

## 4. Prioritized recommendation

**P0 (do next, trust & safety):** report + block in messaging. This is the one gap that's both a real user-safety issue today (messaging shipped without it) and directly evidenced as a baseline expectation across every competitor researched.

**P1:** basic rate limiting on `/api/auth/*`, `/api/reviews`, `/api/conversations/*` — cheap to add (a simple in-memory or Redis-backed limiter; Redis is already provisioned, just unused), closes a real abuse vector.

**P1:** SEO basics (`sitemap.xml`, `robots.txt`, per-teacher meta tags, schema.org `Person`/`Service` structured data) — highest-leverage growth lever available, zero ongoing cost.

**P2:** teacher verification, even a lightweight self-attested "ID uploaded, reviewed by admin" tier surfaced honestly as exactly that (not oversold as a background check) — directly modeled on Practo's registry-check pattern, scaled down to what's actually feasible without a paid verification vendor.

**P2:** response-time signal on teacher cards ("usually replies within a few hours") — free, from data already collected.

**P3:** search pagination, security headers (`next.config.js`), server-side password strength check, dark mode, saved teachers, richer filters.

None of this has been implemented in this pass — this is a review and recommendation, pending your prioritization, same as the architecture review before it.
